## Why

Identity Fusion NG is a SailPoint SaaS connector shipped from this repository
as a versioned zip. Today, a version bump in `package.json` has no
coordinated process around it:

- The `## Changelog` block in `README.md` is hand-curated, but the
  existing CI guard (`scripts/ci-check-readme-changelog.cjs`) only
  enforces "if product files changed then README was touched" -- it
  does NOT detect that the version was bumped, nor that a new
  `### X.Y.Z` heading was added under the existing section.
- Files under `docs/` can drift from the released code with nothing
  to catch it. The MkDocs site is rebuilt on every push to `main`
  (`deploy-docs-pages.yml`) regardless of whether the docs reflect
  the current version.
- The GitHub Release body is auto-generated by
  `softprops/action-gh-release` from merged PR titles, completely
  independently of the curated `## Changelog`. The two can -- and do
  -- disagree.
- Nothing tells a maintainer "you bumped the version; you also need
  to update page X of the docs". That knowledge lives in heads.

The result is that a release can ship with a stale README changelog,
docs that don't match the code, and a GitHub Release body that
contradicts both.

This change makes the version-bump process explicit and agent-driven
rather than ad-hoc. The discipline lives in an OpenSpec spec (so it
is reviewable, version-controlled, and machine-readable) and is
executed by a new opencode subagent (so it runs whenever a developer
prepares a version bump, without requiring a CI check).

## What Changes

1. **New capability `version-update-procedure`** -- a single spec
   that codifies the rules every version bump of the connector must
   follow. The spec is written in OpenSpec Requirements + Gherkin
   Scenarios form so it is unambiguous and can be referenced by any
   future agent or automation.

2. **New opencode subagent `.opencode/agents/release-prep.md`** --
   the executor. Reads `openspec/specs/version-update-procedure/spec.md`,
   detects a version bump in `package.json`, gathers the diff since
   the previous version tag, drafts a `### X.Y.Z` block in the
   existing `## Changelog` style, and uses a `src -> docs` scope map
   (defined in `design.md`) to identify the most-affected guide page
   in `docs/`. Always edits that page so the hard "at least one
   `docs/**` file must change" requirement is satisfied.

3. **New opencode command `.opencode/commands/release-prep.md`** --
   the entry point. A thin wrapper that delegates to the
   `release-prep` subagent. Developers run it locally in opencode
   after bumping `package.json`.

4. **No CI changes.** `ci-check-readme-changelog.cjs` and the other
   `new-version-full-review.yml` jobs stay as they are. They are a
   separate "product-files-changed" guard, not a version-bump guard.
   Enforcement is by the agent, not the pipeline, per the project's
   choice.

5. **No new docs page.** The hard "at least one `docs/**` file must
   change" requirement is satisfied by editing the most-affected
   guide page from the `src -> docs` map, not by maintaining a
   dedicated release-notes page. (If a future change wants a
   dedicated `docs/release-notes.md`, it should be its own OpenSpec
   change.)

## Capabilities

### New Capabilities
- `version-update-procedure`: Defines the rules that every version
  bump of the Identity Fusion connector must follow so that the
  README changelog and the MkDocs documentation site stay in
  lockstep with the released code. Specifies that the
  `release-prep` opencode subagent is the executor and that the
  rules are not enforced by CI.

### Modified Capabilities
- None. This change introduces a new capability and does not alter
  the requirements of `attribute-definition-documentation`,
  `fusion-account-attribute-resolution`, or
  `identity-origin-orphan-detection`.
